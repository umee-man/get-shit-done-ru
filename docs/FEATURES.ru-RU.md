## Core-фичи

### 1. Инициализация проекта

**Команда:** `/gsd-new-project [--auto @file.md]`

**Назначение:** Превратить идею пользователя в полностью структурированный проект с research, скоупленными требованиями и фазированной дорожной картой.

**Требования:**
- REQ-INIT-01: Система ДОЛЖНА проводить адаптивные вопросы пока scope проекта полностью не понят
- REQ-INIT-02: Система ДОЛЖНА спавнить параллельных research-агентов для исследования доменной экосистемы
- REQ-INIT-03: Система ДОЛЖНА извлекать требования в категории v1 (must-have), v2 (future) и out-of-scope
- REQ-INIT-04: Система ДОЛЖНА генерировать фазовую дорожную карту с traceability требований
- REQ-INIT-05: Система ДОЛЖНА требовать одобрения дорожной карты пользователем до продолжения
- REQ-INIT-06: Система ДОЛЖНА предотвращать ре-инициализацию когда `.planning/PROJECT.md` уже существует
- REQ-INIT-07: Система ДОЛЖНА поддерживать флаг `--auto @file.md` для пропуска интерактивных вопросов и извлечения из документа

**Производит:**
| Артефакт | Описание |
|----------|----------|
| `PROJECT.md` | Видение проекта, ограничения, технические решения, правила эволюции |
| `REQUIREMENTS.md` | Скоупленные требования с уникальными ID (REQ-XX) |
| `ROADMAP.md` | Разбивка по фазам с отслеживанием статуса и маппингом требований |
| `STATE.md` | Начальное состояние проекта с позицией, решениями, метриками |
| `config.json` | Конфигурация workflow |
| `research/SUMMARY.md` | Синтезированное доменное исследование |
| `research/STACK.md` | Исследование технического стека |
| `research/FEATURES.md` | Паттерны реализации фич |
| `research/ARCHITECTURE.md` | Архитектурные паттерны и trade-off'ы |
| `research/PITFALLS.md` | Типичные режимы сбоя и митигации |

**Процесс:**
1. **Вопросы** — Адаптивные вопросы по философии "dream extraction" (не сбор требований)
2. **Research** — 4 параллельных researcher-агента исследуют stack, features, architecture, pitfalls
3. **Синтез** — Research synthesizer объединяет находки в SUMMARY.md
4. **Требования** — Извлечены из ответов пользователя + research, категоризированы по scope
5. **Roadmap** — Phase-разбивка, замапленная на требования, granularity-настройка контролирует число фаз

**Функциональные требования:**
- Вопросы адаптируются под детектированный тип проекта (web-app, CLI, mobile, API и т.д.)
- Research-агенты имеют web search возможность для актуальной экосистемной информации
- Granularity-настройка контролирует число фаз: `coarse` (3-5), `standard` (5-8), `fine` (8-12)
- `--auto` режим извлекает всю информацию из предоставленного документа без интерактивных вопросов
- Контекст существующей кодовой базы (от `/gsd-map-codebase`) загружается если присутствует

### 2. Phase Discussion

**Команда:** `/gsd-discuss-phase [N] [--auto] [--batch]`

**Назначение:** Захватить предпочтения и решения пользователя по реализации до начала research'а и планирования. Устраняет серые зоны, заставляющие AI гадать.

**Требования:**
- REQ-DISC-01: Система ДОЛЖНА анализировать scope фазы и идентифицировать decision-области (серые зоны)
- REQ-DISC-02: Система ДОЛЖНА категоризировать серые зоны по типу (visual, API, content, organization и т.д.)
- REQ-DISC-03: Система ДОЛЖНА задавать только вопросы, не отвеченные в предыдущих CONTEXT.md
- REQ-DISC-04: Система ДОЛЖНА persist'ить решения в `{phase}-CONTEXT.md` с каноническими ссылками
- REQ-DISC-05: Система ДОЛЖНА поддерживать флаг `--auto` для авто-выбора рекомендованных дефолтов
- REQ-DISC-06: Система ДОЛЖНА поддерживать флаг `--batch` для группового вопросного intake
- REQ-DISC-07: Система ДОЛЖНА сканить релевантные source-файлы до идентификации серых зон (code-aware обсуждение)
- REQ-DISC-08: Система ДОЛЖНА адаптировать язык серых зон в product-outcome термины когда USER-PROFILE.md указывает на нетехнического владельца (learning_style: guided, jargon в frustration_triggers или high-level explanation depth)
- REQ-DISC-09: Когда REQ-DISC-08 применяется, advisor_research rationale-параграфы ДОЛЖНЫ быть переписаны на plain language — те же решения, переведённый frame

**Производит:** `{padded_phase}-CONTEXT.md` — Предпочтения пользователя, идущие в research и планирование

**Категории серых зон:**
| Категория | Примеры решений |
|-----------|-----------------|
| Visual-фичи | Layout, плотность, взаимодействия, empty states |
| API/CLI | Формат ответа, флаги, обработка ошибок, verbosity |
| Content-системы | Структура, тон, глубина, flow |
| Организация | Критерии группировки, именование, дубликаты, исключения |

### 3. UI дизайн-контракт

**Команда:** `/gsd-ui-phase [N]`

**Назначение:** Зафиксировать дизайн-решения до планирования, чтобы все компоненты в фазе шарили согласованные визуальные стандарты.

**Требования:**
- REQ-UI-01: Система ДОЛЖНА детектить существующее состояние дизайн-системы (shadcn components.json, Tailwind config, токены)
- REQ-UI-02: Система ДОЛЖНА задавать только неотвеченные дизайн-контракт вопросы
- REQ-UI-03: Система ДОЛЖНА валидировать против 6 измерений (Copywriting, Visuals, Color, Typography, Spacing, Registry Safety)
- REQ-UI-04: Система ДОЛЖНА входить в revision-цикл если валидация возвращает BLOCKED (макс 2 итерации)
- REQ-UI-05: Система ДОЛЖНА предлагать shadcn-инициализацию для React/Next.js/Vite-проектов без `components.json`
- REQ-UI-06: Система ДОЛЖНА форсить registry safety gate для third-party shadcn-реестров

**Производит:** `{padded_phase}-UI-SPEC.md` — Дизайн-контракт, потребляемый исполнителями

**6 измерений валидации:**
1. **Copywriting** — CTA-лейблы, empty states, error-сообщения
2. **Visuals** — Фокальные точки, визуальная иерархия, доступность иконок
3. **Color** — Дисциплина акцентов, соблюдение 60/30/10
4. **Typography** — Соблюдение ограничений размера/веса шрифта
5. **Spacing** — Выравнивание по сетке, согласованность токенов
6. **Registry Safety** — Требования инспекции third-party компонентов

**shadcn-интеграция:**
- Детектит отсутствующий `components.json` в React/Next.js/Vite-проектах
- Ведёт пользователя через настройку preset на `ui.shadcn.com/create`
- Preset-строка становится планировочным артефактом, воспроизводимым между фазами
- Safety gate требует `npx shadcn view` и `npx shadcn diff` перед third-party компонентами

### 4. Планирование фазы

**Команда:** `/gsd-plan-phase [N] [--auto] [--skip-research] [--skip-verify]`

**Назначение:** Исследовать домен реализации и произвести верифицированные, атомарные execution-планы.

**Требования:**
- REQ-PLAN-01: Система ДОЛЖНА спавнить phase-researcher'а для исследования подходов реализации
- REQ-PLAN-02: Система ДОЛЖНА производить планы по 2-3 задачи каждый, размером под одно контекстное окно
- REQ-PLAN-03: Система ДОЛЖНА структурировать планы как XML с элементами `<task>`, содержащими поля `name`, `files`, `action`, `verify`, `done`
- REQ-PLAN-04: Система ДОЛЖНА включать секции `read_first` и `acceptance_criteria` в каждом плане
- REQ-PLAN-05: Система ДОЛЖНА запускать plan checker verification loop (до 3 итераций) если не установлено `--skip-verify`
- REQ-PLAN-06: Система ДОЛЖНА поддерживать флаг `--skip-research` для обхода research-фазы
- REQ-PLAN-07: Система ДОЛЖНА промптить пользователя запустить `/gsd-ui-phase` если детектирована frontend-фаза и UI-SPEC.md отсутствует (UI safety gate)
- REQ-PLAN-08: Система ДОЛЖНА включать Nyquist validation mapping когда `workflow.nyquist_validation` включено
- REQ-PLAN-09: Система ДОЛЖНА верифицировать что все требования фазы покрыты хотя бы одним планом до завершения планирования (requirements coverage gate)

**Производит:**
| Артефакт | Описание |
|----------|----------|
| `{phase}-RESEARCH.md` | Находки экосистемного research'а |
| `{phase}-{N}-PLAN.md` | Атомарные execution-планы (2-3 задачи каждый) |
| `{phase}-VALIDATION.md` | Маппинг тест-покрытия (Nyquist-слой) |

**Структура плана (XML):**
```xml
<task type="auto">
  <name>Create login endpoint</name>
  <files>src/app/api/auth/login/route.ts</files>
  <action>
    Use jose for JWT. Validate credentials against users table.
    Return httpOnly cookie on success.
  </action>
  <verify>curl -X POST localhost:3000/api/auth/login returns 200 + Set-Cookie</verify>
  <done>Valid credentials return cookie, invalid return 401</done>
</task>
```

**Plan Checker верификация (8 измерений):**
1. Покрытие требований — Планы адресуют все требования фазы
2. Атомарность задач — Каждая задача независимо коммитима
3. Порядок зависимостей — Задачи секвенциированы корректно
4. File scope — Нет избыточного file-overlap между планами
5. Verification-команды — У каждой задачи тестируемые done-критерии
6. Context fit — Задачи помещаются в одно контекстное окно
7. Gap-детекция — Нет недостающих шагов реализации
8. Nyquist-комплаенс — У задач есть автоматические verify-команды (когда включено)

### 5. Исполнение фазы

**Команда:** `/gsd-execute-phase <N>`

**Назначение:** Исполнить все планы в фазе используя wave-based параллелизацию со свежими контекстными окнами на каждого исполнителя.

**Требования:**
- REQ-EXEC-01: Система ДОЛЖНА анализировать зависимости планов и группировать в execution-волны
- REQ-EXEC-02: Система ДОЛЖНА спавнить независимые планы параллельно в пределах каждой волны
- REQ-EXEC-03: Система ДОЛЖНА давать каждому исполнителю свежее контекстное окно (200K токенов)
- REQ-EXEC-04: Система ДОЛЖНА производить атомарные git-коммиты на задачу
- REQ-EXEC-05: Система ДОЛЖНА производить SUMMARY.md для каждого завершённого плана
- REQ-EXEC-06: Система ДОЛЖНА запускать post-execution verifier для проверки достижения целей фазы
- REQ-EXEC-07: Система ДОЛЖНА поддерживать git-стратегии ветвления (`none`, `phase`, `milestone`)
- REQ-EXEC-08: Система ДОЛЖНА вызывать node repair operator на task verification failure (когда включено)
- REQ-EXEC-09: Система ДОЛЖНА запускать test-suite'ы предыдущих фаз до верификации чтобы поймать cross-phase регрессии

**Производит:**
| Артефакт | Описание |
|----------|----------|
| `{phase}-{N}-SUMMARY.md` | Outcome'ы исполнения на план |
| `{phase}-VERIFICATION.md` | Отчёт постфактум-верификации |
| Git-коммиты | Атомарные коммиты на задачу |

**Wave Execution:**
- Планы без зависимостей → Wave 1 (параллельно)
- Планы, зависящие от Wave 1 → Wave 2 (параллельно, ждёт Wave 1)
- Продолжается пока все планы не завершены
- File-конфликты форсят последовательное исполнение в той же волне

**Возможности исполнителя:**
- Читает PLAN.md с полными инструкциями задач
- Имеет доступ к PROJECT.md, STATE.md, CONTEXT.md, RESEARCH.md
- Коммитит каждую задачу атомарно со структурированными commit-сообщениями
- Использует `--no-verify` на коммитах во время параллельного исполнения чтобы избежать build lock contention
- Обрабатывает типы чекпоинтов: `auto`, `checkpoint:human-verify`, `checkpoint:decision`, `checkpoint:human-action`
- Репортит отклонения от плана в SUMMARY.md

**Параллельная безопасность:**
- **Pre-commit хуки**: Пропускаются параллельными агентами (`--no-verify`), запускаются один раз оркестратором после каждой волны
- **STATE.md locking**: File-level lockfile предотвращает порчу при конкурентной записи между агентами

### 6. Верификация работы

**Команда:** `/gsd-verify-work [N]`

**Назначение:** User acceptance testing — проводит пользователя через тестирование каждой поставки и авто-диагностирует падения.

**Требования:**
- REQ-VERIFY-01: Система ДОЛЖНА извлекать тестируемые поставки из фазы
- REQ-VERIFY-02: Система ДОЛЖНА презентовать поставки по одной для подтверждения пользователем
- REQ-VERIFY-03: Система ДОЛЖНА спавнить debug-агентов для авто-диагностики падений
- REQ-VERIFY-04: Система ДОЛЖНА создавать fix-планы для идентифицированных проблем
- REQ-VERIFY-05: Система ДОЛЖНА инжектить cold-start smoke test для фаз, модифицирующих server/database/seed/startup файлы
- REQ-VERIFY-06: Система ДОЛЖНА производить UAT.md с pass/fail результатами

**Производит:** `{phase}-UAT.md` — Результаты UAT, плюс fix-планы если найдены проблемы

### 6.5. Ship

**Команда:** `/gsd-ship [N] [--draft]`

**Назначение:** Мост между локальным завершением и смердженным PR. После прохождения верификации — push ветки, создание PR с авто-генерируемым телом из планировочных артефактов, опционально триггер ревью и отслеживание в STATE.md.

**Требования:**
- REQ-SHIP-01: Система ДОЛЖНА верифицировать что фаза прошла верификацию до shipping'а
- REQ-SHIP-02: Система ДОЛЖНА push'ить ветку и создавать PR через CLI `gh`
- REQ-SHIP-03: Система ДОЛЖНА авто-генерировать тело PR из SUMMARY.md, VERIFICATION.md, REQUIREMENTS.md
- REQ-SHIP-04: Система ДОЛЖНА обновлять STATE.md со статусом shipping'а и номером PR
- REQ-SHIP-05: Система ДОЛЖНА поддерживать флаг `--draft` для черновых PR
- REQ-SHIP-06: Система ДОЛЖНА поддерживать append-only project PR body-секции, сконфигурированные в `ship.pr_body_sections`

**Предусловия:** Фаза верифицирована, CLI `gh` установлен и авторизован, работа на feature-ветке

**Производит:** GitHub PR с богатым телом, опциональными PRD-style секциями, STATE.md обновлён

**Пользовательская документация:** [Custom PR Body Sections](ship-pr-body-sections.md)

### 7. UI Review

**Команда:** `/gsd-ui-review [N]`

**Назначение:** Ретроактивный 6-компонентный визуальный аудит имплементированного frontend-кода. Работает standalone на любом проекте.

**Требования:**
- REQ-UIREVIEW-01: Система ДОЛЖНА оценивать каждый из 6 столпов по шкале 1-4
- REQ-UIREVIEW-02: Система ДОЛЖНА снимать скриншоты через Playwright CLI в `.planning/ui-reviews/`
- REQ-UIREVIEW-03: Система ДОЛЖНА создавать `.gitignore` для директории скриншотов
- REQ-UIREVIEW-04: Система ДОЛЖНА идентифицировать топ-3 приоритетных фикса
- REQ-UIREVIEW-05: Система ДОЛЖНА работать standalone (без UI-SPEC.md) используя абстрактные стандарты качества

**6 столпов аудита (оцениваются 1-4):**

## Quality Assurance фичи

### 15. Nyquist валидация

**Назначение:** Замаппить покрытие автотестами на требования фазы до того как написана хоть строчка кода. Назван по теореме Найквиста — гарантирует что для каждого требования существует feedback-сигнал.

**Требования:**
- REQ-NYQ-01: Система ДОЛЖНА детектить существующую тест-инфраструктуру во время research'а plan-phase
- REQ-NYQ-02: Система ДОЛЖНА маппить каждое требование на конкретную тест-команду
- REQ-NYQ-03: Система ДОЛЖНА идентифицировать Wave 0 задачи (test-каркас, нужный до реализации)
- REQ-NYQ-04: Plan checker ДОЛЖЕН форсить Nyquist-комплаенс как 8-е verification-измерение
- REQ-NYQ-05: Система ДОЛЖНА поддерживать ретроактивную валидацию через `/gsd-validate-phase`
- REQ-NYQ-06: Система ДОЛЖНА отключаться через `workflow.nyquist_validation: false`

**Производит:** `{phase}-VALIDATION.md` — Контракт тест-покрытия

**Ретроактивная валидация (`/gsd-validate-phase [N]`):**
- Сканит реализацию и маппит требования на тесты
- Идентифицирует пробелы, где требования лишены автоматической верификации
- Спавнит auditor для генерации тестов (макс 3 попытки)
- Никогда не модифицирует implementation-код — только test-файлы и VALIDATION.md
- Флагает баги реализации как эскалации для адресации пользователем

## Context Engineering фичи

### 22. Мониторинг контекстного окна

**Назначение:** Предотвратить context rot, алертя и пользователя, и агента, когда контекст истекает.

**Требования:**
- REQ-CTX-01: Statusline ДОЛЖЕН отображать процент использования контекста пользователю
- REQ-CTX-02: Context monitor ДОЛЖЕН инжектить agent-facing предупреждения на ≤35% остатка (WARNING)
- REQ-CTX-03: Context monitor ДОЛЖЕН инжектить agent-facing предупреждения на ≤25% остатка (CRITICAL)
- REQ-CTX-04: Предупреждения ДОЛЖНЫ дебаунситься (5 tool-вызовов между повторными предупреждениями)
- REQ-CTX-05: Эскалация severity (WARNING→CRITICAL) ДОЛЖНА обходить дебаунс
- REQ-CTX-06: Context monitor ДОЛЖЕН различать GSD-active vs не-GSD-active проекты
- REQ-CTX-07: Предупреждения ДОЛЖНЫ быть advisory, никогда императивные команды, override'ящие предпочтения пользователя
- REQ-CTX-08: Все хуки ДОЛЖНЫ падать молча и никогда не блокировать tool-исполнение

**Архитектура:** Двухчастная bridge-система:
1. Statusline пишет метрики в `/tmp/claude-ctx-{session}.json`
2. Context monitor читает метрики и инжектит `additionalContext` предупреждения

### 26. Профили моделей

**Команда:** `/gsd-config --profile <quality|balanced|budget|adaptive|inherit>`

**Назначение:** Контролировать какую AI-модель использует каждый агент, балансируя качество vs стоимость.

**Требования:**

- REQ-MODEL-02: Каждый профиль ДОЛЖЕН определять model tier per агента (см. profile-таблицу)
- REQ-MODEL-03: Per-agent override'ы ДОЛЖНЫ иметь приоритет над профилем
- REQ-MODEL-04: Профиль `inherit` ДОЛЖЕН откладывать выбор на текущую модель рантайма

- REQ-MODEL-06: Резолв моделей ДОЛЖЕН происходить один раз на оркестрацию, не на спавн

**Инкрементальный remap — `--paths` (#2003):** Mapper принимает опциональный scope-hint `--paths <p1,p2,...>`. Когда предоставлен, ограничивает исследование перечисленными repo-относительными префиксами вместо сканирования всего дерева. Это путь, используемый post-execute codebase-drift gate для рефреша только тех поддеревьев, которые фаза фактически изменила. Каждый произведённый документ несёт `last_mapped_commit` в своём YAML frontmatter, чтобы дрейф мерился относительно mapping-точки, а не HEAD.

### 27a. Post-Execute Codebase Drift Detection

**Введено:** #2003
**Триггер:** Работает автоматически в конце каждого `/gsd-execute-phase`
**Конфигурация:**
- `workflow.drift_threshold` (integer, дефолт `3`) — минимум новых структурных элементов до того как gate действует
- `workflow.drift_action` (`warn` | `auto-remap`, дефолт `warn`) — warn-only или спавн `gsd-codebase-mapper` с `--paths`, скоупленным под затронутые поддеревья

**Что считается дрейфом:**
- Новая директория вне отмаппленных путей
- Новый barrel-экспорт в `(packages|apps)/*/src/index.*`
- Новый migration-файл (supabase/prisma/drizzle/src/migrations/…)
- Новый route-модуль под `routes/` или `api/`

**Не-блокирующая гарантия:** любое внутреннее падение (missing STRUCTURE.md, git-ошибки, mapper spawn failure) логирует одну строку, и фаза продолжается. Drift-детекция не может провалить верификацию.

**Требования:**
- REQ-DRIFT-01: Система ДОЛЖНА детектить четыре drift-категории из `git diff --name-status last_mapped_commit..HEAD`
- REQ-DRIFT-02: Действие срабатывает только когда количество элементов ≥ `workflow.drift_threshold`
- REQ-DRIFT-03: Действие `warn` НЕ ДОЛЖНО спавнить любого агента
- REQ-DRIFT-04: Действие `auto-remap` ДОЛЖНО передавать санитизированный `--paths` в mapper
- REQ-DRIFT-05: Падение детекции/remap'а ДОЛЖНО быть не-блокирующим для `/gsd-execute-phase`
- REQ-DRIFT-06: `last_mapped_commit` round-trip через YAML frontmatter в каждом файле `.planning/codebase/*.md`

### 39. Execution Hardening

**Назначение:** Три аддитивных улучшения качества пайплайна исполнения, ловящие cross-plan падения до того как они каскадируются.

**Компоненты:**

**1. Pre-Wave Dependency Check** (execute-phase)
Перед спавном волны N+1 верифицировать что key-links из артефактов предыдущей волны существуют и проводны корректно. Ловит cross-plan dependency-пробелы до того как они каскадируют в downstream-падения.

**2. Cross-Plan Data Contracts — Dimension 9** (plan-checker)
Новое analysis-измерение, проверяющее что планы, шарящие data-пайплайны, имеют совместимые трансформации. Флагает когда один план стрипит данные, нужные другому плану в оригинальной форме.

**3. Export-Level Spot Check** (verify-phase)
После прохождения Level 3 wiring-верификации, spot-check'ить индивидуальные экспорты на фактическое использование. Ловит dead stores, существующие в wired-файлах, но никогда не вызываемые.

**Требования:**
- REQ-HARD-01: Pre-wave check ДОЛЖЕН верифицировать key-links из всех артефактов предыдущих волн до спавна следующей волны
- REQ-HARD-02: Cross-plan contract check ДОЛЖЕН детектить несовместимые data-трансформации между планами
- REQ-HARD-03: Export spot-check ДОЛЖЕН идентифицировать dead stores в wired-файлах

### 40. Трекинг verification-долга

**Команда:** `/gsd-audit-uat`

**Назначение:** Предотвратить молчаливую потерю UAT/verification-айтемов когда проекты продвигаются мимо фаз с outstanding-тестами. Всплывает verification-долг по всем предыдущим фазам, чтобы айтемы никогда не забывались.

**Компоненты:**

**1. Cross-Phase Health Check** (progress.md Step 1.6)
Каждый вызов `/gsd-progress` сканит ВСЕ фазы в текущем майлстоуне на outstanding-айтемы (pending, skipped, blocked, human_needed). Отображает не-блокирующую warning-секцию с actionable-ссылками.

**2. `status: partial`** (verify-work.md, UAT.md)
Новый UAT-статус, различающий "сессия закончилась" и "все тесты решены". Предотвращает `status: complete` когда тесты ещё pending, blocked или skipped без причины.

**3. `result: blocked` с `blocked_by` тегом** (verify-work.md, UAT.md)
Новый тип результата теста для тестов, заблокированных внешними зависимостями (сервер, физическое устройство, release-build, third-party сервисы). Категоризируется отдельно от skipped-тестов.

**4. Персистенция HUMAN-UAT.md** (execute-phase.md)
Когда верификация возвращает `human_needed`, айтемы персистятся как отслеживаемый HUMAN-UAT.md файл со `status: partial`. Кормит cross-phase health check и audit-системы.

**5. Phase Completion Warnings** (phase.cjs, transition.md)
`phase complete` CLI возвращает предупреждения verification-долга в своём JSON-выводе. Transition-workflow всплывает outstanding-айтемы до подтверждения.

**Требования:**
- REQ-DEBT-01: Система ДОЛЖНА всплывать outstanding UAT/verification-айтемы из ВСЕХ предыдущих фаз в `/gsd-progress`
- REQ-DEBT-02: Система ДОЛЖНА различать незавершённое тестирование (partial) от завершённого (complete)
- REQ-DEBT-03: Система ДОЛЖНА категоризировать заблокированные тесты с `blocked_by` тегами
- REQ-DEBT-04: Система ДОЛЖНА персистить human_needed verification-айтемы как отслеживаемые UAT-файлы
- REQ-DEBT-05: Система ДОЛЖНА предупреждать (не-блокирующе) во время завершения фазы и transition'а когда verification-долг существует
- REQ-DEBT-06: `/gsd-audit-uat` ДОЛЖЕН сканить все фазы, категоризировать айтемы по тестируемости и производить human test plan
